# Community and engineering sources

Status: resolved
Type: research

## Evidence

Every vendor source is a release-notes feed, so the report has no commentary, practice or discussion. The vendor product blogs were rejected in ticket 01 because they repeat the release notes; that reason does not cover engineering blogs or community sources.

## Question

Which sources add data engineering news and opinion at a useful volume, and how are they judged?

Candidates to check (feed exists, items a week, share relevant to a data engineer at a Databricks/Snowflake/Azure/GCP consultancy):

- Hacker News, Lobste.rs (`databases` tag) and r/dataengineering, filtered by data terms (DuckDB, Iceberg, lakehouse, dbt, Spark, Postgres…). The HN and Lobste.rs fetchers exist (`src/sources/`).
- Engineering blogs: DuckDB, dbt, Apache Iceberg, the Databricks and Snowflake engineering blogs (not the product blogs).
- One or two newsletters, e.g. Data Engineering Weekly.

## Done when

- A spike note in this file (`## Answer`): per candidate, feed URL, items over the last 14 days, how many a data engineer would want, and the overlap with the vendor feeds.
- A recommendation: which to add, the section they go in (a `## News & discussion` table like Policy Watch's News & commentary is the default), and the Jev question(s) that judge them, reusing `selectVendorItems`'s pipeline.
- Implementation is a follow-up ticket.

## Answer

Spike run 2026-10-30 (a Thursday) from a cloud container, every request with `User-Agent: Mozilla/5.0 daily-diff/1.0`. Volumes are counted from each feed's item dates over the 14 and 28 days before the run; "wanted" is judged from titles: would a Digital Power data engineer open it. Reachability from GitHub Actions is _unverified_ for every source. HN, Lobste.rs and Dev.to already reach the page through Spotted and project news, so they were not re-measured.

### Recommendation

1. **Add `data.community` to `config.yml`**: RSS feeds with `name`, `url`, optional `kind` (`blog` | `newsletter` | `forum`) and optional `cap` (rows per run; default 1, Snowflake Medium and Reddit 2). Start with the 13 "Use" / "Use with caveat" sources above; drop the dbt Labs blog after two weeks if its kept share stays under 1 in 5.
2. **Route like stories, not like vendor items.** A feed item is a `Story` (`src/spotted/pool.ts`): first `matchProjectNews` (data pool) so "Announcing Polars 2.1" lands as **News** under Polars, next to its release; the rest is judged by Jev and goes in a `## News & discussion` table (Story | Source | Summary) after `## Across platforms` and before `## Spotted`. HN/Lobste.rs stories keep going through Spotted unchanged. A blog item never makes the report on its own (like Spotted and EU data law).
3. **Jev questions**, through `judgeItems` with a new `digests/community-verdicts.json` (asked again never; pruned after 30 days): `insight` (does the post teach a data engineer something about building or running a data platform: a technique, a measured result, a migration, a failure; vs a customer story, event, hiring or product announcement) as a score with confidence, and `audience` (Databricks / Snowflake / Azure-Fabric / GCP / open-source stack / general data engineering / off-audience). Keep bar: insight ≥ 0.6 and not off-audience; a release announcement that duplicates a tracked repo's release of the same day is dropped in code (`repeat`, by link to the repo's release or by title naming the tag).
4. **Caps**: at most 6 rows, 1 per source by default (`cap`), newest first; a trace file `community-trace.json` like the others.
5. **Newsletters** (Data Engineering Weekly) are one row per issue with the LLM summary written from the issue's description; the feed's item text is a link list, so `vendorText`-style truncation at 1,000 characters is enough.
6. Expected volume: ~8–12 candidate items a day across all feeds, of which 2–4 kept on a typical day, 0 on many weekend days.
