# Community and engineering sources

Status: resolved
Type: research

## Evidence

Every vendor source is a release-notes feed, so the report has no commentary, practice or discussion. The vendor product blogs were rejected in ticket 01 because they repeat the release notes; that reason does not cover engineering blogs or community sources.

## Question

Which sources add data engineering news and opinion at a useful volume, and how are they judged?

Candidates to check (feed exists, items a week, share relevant to a data engineer at a Databricks/Snowflake/Azure/GCP consultancy):

- Hacker News, Lobste.rs (`databases` tag) and r/dataengineering, filtered by data terms (DuckDB, Iceberg, lakehouse, dbt, Spark, Postgres…). The HN and Lobste.rs fetchers exist (`src/sources/`).
- Engineering blogs: DuckDB, dbt, Apache Iceberg, the Databricks and Snowflake engineering blogs (not the product blogs).
- One or two newsletters, e.g. Data Engineering Weekly.

## Done when

- A spike note in this file (`## Answer`): per candidate, feed URL, items over the last 14 days, how many a data engineer would want, and the overlap with the vendor feeds.
- A recommendation: which to add, the section they go in (a `## News & discussion` table like Policy Watch's News & commentary is the default), and the Jev question(s) that judge them, reusing `selectVendorItems`'s pipeline.
- Implementation is a follow-up ticket.

## Answer

Spike run 2026-10-30 (a Thursday) from a cloud container, every request with `User-Agent: Mozilla/5.0 daily-diff/1.0`. Volumes are counted from each feed's item dates over the 14 and 28 days before the run; "wanted" is judged from titles: would a Digital Power data engineer open it. Reachability from GitHub Actions is _unverified_ for every source except where noted: `spec.md` (Out of Scope) records that Substack answered HTTP 403 to every GitHub Actions run when tried for Policy Watch, so the Substack rows below are dropped on that ground, and Reddit is out of scope there too.

### The sources already on the page

HN, Lobste.rs and Dev.to reach the data page through project news and Spotted. Measured from `digests/spotted-log.json` and `spotted-verdicts.json` for its 8-day window (2026-10-23..10-30): 285 stories fetched (232 HN, 12 Lobste.rs, 41 Dev.to), 12 routed to the `data` topic by Jev (7 HN, 4 Lobste.rs, 1 Dev.to), 11 shown as Spotted rows (0 on five of the twelve report days 2026-10-19..10-30). That is about 1.5 community stories a day for the page, all of them whatever happened to reach HN's top 500 or the Lobste.rs `databases` tag: no engineering blog reaches the page unless someone submits it.

### Recommendation

1. **Add `data.community` to `config.yml`**: RSS feeds with `name`, `url`, optional `kind` (`blog` | `newsletter`) and optional `cap` (rows per run; default 1, Snowflake Medium 2). Start with the 10 "Use" / "Use with caveat" sources above: DuckDB, Polars, Airflow, dbt Developer, dbt Labs (caveat), dltHub (caveat), Dagster, Confluent (caveat), OpenMetadata, Snowflake on Medium (caveat). Measure the dbt Labs blog's kept share over its first two weeks in `community-trace.json` (ticket 14 names the check); under 1 in 5 it is removed.
2. **Route like stories, not like vendor items.** The ticket asked to reuse `selectVendorItems`'s pipeline. That pipeline is built for release notes: its questions are "real change / deprecation / AI in data / significance", its state key is title + date, and its sections are per vendor; none of that fits an essay or a blog post, and a blog post about a tracked project belongs next to that project, not in a vendor table. So a feed item is a `Story` (`src/spotted/pool.ts`): first `matchProjectNews` (data pool) so "Announcing Polars 2.1" lands as **News** under Polars, next to its release; the rest is judged by Jev and goes in a `## News & discussion` table (Story | Source | Summary) after `## Across platforms` and before `## Spotted`. What is reused is `judgeItems` (verdict cache, trace), `summarizeRows` and the drop reasons. HN/Lobste.rs stories keep going through Spotted unchanged. A blog item never makes the report on its own (like Spotted and EU data law).
3. **Jev questions**, through `judgeItems` with a new `digests/community-verdicts.json` (asked again never; pruned after 30 days): `insight` (does the post teach a data engineer something about building or running a data platform: a technique, a measured result, a migration, a failure; vs a customer story, event, hiring or product announcement) as a score with confidence, and `audience` (Databricks / Snowflake / Azure-Fabric / GCP / open-source stack / general data engineering / off-audience). Keep bar: insight ≥ 0.6 and not off-audience; a release announcement that duplicates a tracked repo's release of the same day is dropped in code (`repeat`, by link to the repo's release or by title naming the tag).
4. **Caps**: at most 6 rows, 1 per source by default (`cap`), newest first; a trace file `community-trace.json` like the others.
5. Expected volume from the 10 feeds: ~4–8 candidate items a day (the dbt Labs blog's Coalesce burst aside), of which 1–3 kept on a typical day, 0 on many weekend days.
6. **Reachability from Actions is the first implementation step**: fetch every configured feed from a `workflow_dispatch` run before building on them (the Fabric community blog answered 403 to this container, the Commission site answers 403 to Actions only).

Implementation is ticket 14.
