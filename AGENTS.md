# AGENTS.md

## Project overview

Daily Diff is a daily digest generator for the AI open-source ecosystem, AI policy, and the data engineering stack of the maintainer's colleagues at Digital Power (Databricks, Snowflake, the open-source data tools). A GitHub Actions cron job is set for 01:07 Europe/Amsterdam (GitHub starts it 2.5–4 h late, so the digest lands by about 05:00 Amsterdam time) and produces English reports, published as GitHub Issues and committed Markdown files. Most reports are daily; the Trends page runs weekly, on Mondays (CST).

Each module's comments carry its API details and the reasons behind its filters and thresholds. This file holds what spans files: the pipeline, the shared state and verdict caches, the decisions, and how to fix things by hand.

## Commands

```bash
pnpm start          # run the full digest locally
pnpm test           # vitest (unit tests)
pnpm typecheck      # tsc --noEmit
pnpm lint           # ESLint
pnpm lint:fix       # ESLint --fix
pnpm format         # Prettier --write src
pnpm format:check   # Prettier --check src
pnpm readme         # regenerate README's tracked-repo tables from config.yml (--check: fail if stale)
```

## Architecture

The pipeline runs in four sequential phases in `src/index.ts`:

1. **`fetchAllData`**: all network I/O in parallel. No fetcher throws: a failure is its empty value with `fetchSuccess: false`, so `fetchAllData` has no fallbacks. The weekly-only fetches (Skills, OpenRouter apps and rankings, npm, Hugging Face, the trending topic search and the Trends ranking, `composeTrendingReport`) are gated on `isWeeklyRun`.
2. **News matching and Spotted routing**: `matchProjectNews` (`src/reports/project-news.ts`) assigns the fresh community stories (`freshStories`) and GitHub Trending repos to the projects they name, once for the agents and infra projects and once for the data projects (a separate pool). The fresh stories no project and no listed lab post took (`splitPool`) are routed to a topic by Jev (`routeStories`) and selected for their page's Spotted table (`selectSpotted`).
3. **Agents and Spotted summaries**: one LLM call per agents-report section and one for every page's Spotted rows and, on a weekly run, Trends' Most discussed rows (numbered after them), made in `main()` before the page builders, so the pages' Highlights calls see their Spotted tables.
4. **Save phase**: the `buildXxxReport` functions (`src/reports/pages.ts`) make every other LLM call (row summaries first, then a Highlights/prose call over the rendered page) and return the reports. Some builders already save state: the labs and models states, AI Policy's and the data report's observed state, verdicts and traces, the trending trace. `main()` then runs the LLM health gate, adds each report bar (`renderReportBar`), writes the reports and the remaining state files (Spotted log, Spotted verdicts, ArXiv and research states), generates `highlights.json` and `coming-up.json`, and opens the GitHub Issues.

Every chat-model call goes through `callLlm` (`src/core/llm.ts`), at most 5 concurrent.

## Tracked sources

### Jev verdict caches

Every Jev judgment except ArXiv's goes through `judgeItems` (`src/core/jev.ts`) and caches Jev's raw answers per item in a committed file, one item per line:

| File                             | Judgment                    | Asked again when        | Pruned after |
| -------------------------------- | --------------------------- | ----------------------- | ------------ |
| `digests/policy-verdicts.json`   | AI Policy relevance         | the stage changes       | 30 days      |
| `digests/data-verdicts.json`     | vendor item relevance       | the text gains dates    | 30 days      |
| `digests/trending-verdicts.json` | trending scope and category | the description changes | 180 days     |
| `digests/spotted-verdicts.json`  | Spotted topic               | never                   | 30 days      |

- **To fix a verdict**, edit its `answers` and set `"pinned": true`, so it is never asked again. A score answer's `probabilities` decide AI Policy's impact and `other` gates, so edit them too (or delete them, and its `score` decides). To have Jev ask again, delete the entry.
- A file that fails to parse means every item is asked and the file is left as it is.
- Without `TYPESAFE_API_KEY`, or with more than half the new calls failing, each judgment falls back to keyword rules (trending: the search topic label) for the items without a saved verdict. Saved verdicts are always used.
- `digests/trending-matches.json` holds Jev's OpenRouter app → npm package / GitHub repo matches, outside `judgeItems`: a malformed file turns matching off for the run and is left as it is. Code never overwrites a match. **To fix a wrong match**, delete its `npm` or `github` field and add the key (`npm:<name>` or `github:<owner/repo>`) to `rejected`; to force one, set the field.
- ArXiv scores papers with Jev directly, uncached. Jev is not a chat model, so it bypasses `callLlm` and `llmStats`. When more than half the calls fail, a request Jev rejects (HTTP 400 from a malformed question) included, ArXiv ranks by recency and saves no papers to the research state that day (`[arxiv] Too many Jev failures … ranked by recency` in the log, the first error just above it).

### Reported state

- AI Policy (`digests/policy-state.json`), the data report (`digests/data-state.json`), the models page (`digests/models-state.json`) and the hot issues of every repo section (`digests/hot-issues-state.json`) share `ReportedState` (`src/core/report-state.ts`): item id → CST date first reported, pruned after 30 days (the hot-issue state is never pruned). `stages` (id → stage key, never pruned) makes a stage item new again when its stage moves.
- `digests/hot-issues-snapshot.json` is not a `ReportedState`: per issue (`<owner/repo>#<n>`) the `comments + 👍` total of every issue a repo's hot-issue list returned, with the CST date seen and `baseline`, the last total from an earlier day, so a same-day re-run measures the same gains. One entry per line, written after the LLM health gate for every repo (repeats and unpublished pages included), pruned of entries older than the 2-day baseline age (never read after that); a missing or malformed file reads as empty (logged).
- Every state in `digests/` keeps today's items new, so a same-day re-run reports the same items. A missing or malformed state reads as a first run.
- An item first seen at a stage over 30 days old is record-only (`staleOnFirstSight`): its stage is stored without being reported, so a first run, or a new watchlist entry, does not open with stale news.
- AI Policy and the data report save in two parts (`planWrites`, `src/core/new-items.ts`): what the run observed on every successful fetch, quiet days included; the kept items marked reported only once the report exists.
- AI Policy's deadlines and the data report's Action required dates are kept until their date passes (`nextDeadlines`) and shown on report days only: open deadlines alone never make a report.

### AI Agents (`ai-agents`)

- **Repos**: `agents.repos` and `infra.repos` (agent tooling: sandboxes, session multiplexers, context tools) in `config.yml` (README's tables are generated from it), and nothing else: trending repos are never added (decision of 2026-10-22). Per-repo quirks (no releases, issues disabled, prerelease-only) are comments next to the entry. Optional `keywords` set the news-match terms (Pi needs them: "pi" alone matches Raspberry Pi). A quiet project costs one name in the Quiet line, so pruning is rarely needed.
- **Releases, hot issues and news only, no issue/PR churn**: per-repo summaries of churn mostly restated ongoing themes. Stable releases only (`isPrerelease` checks the API flag and the tag, since several projects publish nightlies as normal releases); a project that never shipped a stable release (`noStableYet`) sends its newest prereleases instead. Releases are read 10 a page (Codex's ~130 assets per release make a page of 100 fail at GitHub's ~10 s limit), until a page ends before the window and a stable release has been seen, at most `RELEASES_MAX_PAGES` (5) pages; `githubGet` retries a 502/503/504, a truncated body and its 30 s timeout like a dropped connection. The model gets each release's notes without links, PR references and contributor lines, the breaking, removed, deprecated, upgrade/migration and security sections first, cut after the last whole item within `RELEASE_BODY_CHARS` (2000).
- **Hot issues** (`fetchHotIssues`): open issues, however old, that gained `comments + 👍` ≥ 10, or ≥ 3 with a regression/security label; at most 2 per repo, highest gain first, and the prompt gets the gain next to the totals and up to 1,000 characters of the body without template lines, code blocks and link URLs (`HOT_ISSUE_BODY_CHARS`); the model writes only `#<number>: <description>`, and code links the issue and appends its regression/security label, totals, gain and fix status in one parenthetical (`withHotIssueFacts`). The candidates are every open issue updated in the window, from the core issues list (`/issues?state=open&since=&sort=updated`, 100 a page, pull requests dropped), read until a short page, at most `HOT_ISSUE_MAX_PAGES` (8) pages per repo (hitting it is logged; on 2026-10-26 Codex and Claude Code each had ~550 issues updated in 24h): those whose total clears the bar (the gain cannot exceed it). Every listed issue's total goes into the snapshot (`digests/hot-issues-snapshot.json`, under Reported state). The gain is, in order: today's total minus the snapshot baseline, when that baseline is at most 2 days old (one from 2 days ago makes the prompt say "since <date>" instead of "in the last 24h"; older entries are pruned); the whole total for an issue opened in the window; else counted by the API, for at most `HOT_ISSUE_MAX_CHECKED` (10) such issues per repo, highest total first, from the comments created in the window (`/comments?since=`, which filters on `updated_at`, so edited old comments are dropped by `created_at`) and the 👍 reactions created in it (the API returns them oldest first, so the last page), by people: a bot's comment or 👍 (`user.type` "Bot" or a `[bot]` login) and a comment that is only a slash command (`/assign`) are not counted. A known gain (snapshot delta or opened-in-window total) that clears the bar is recounted the same way for up to `HOT_ISSUE_MAX_VERIFIED` (4) candidates per repo, highest gain first, out of the same count calls, and the lower of the two is the gain; one not recounted keeps its known gain. That count is up to 3 core calls per issue (comments, the last 👍 page, the page before it for over 100 👍), at most `HOT_ISSUE_MAX_COUNT_CALLS` (250) per run, shared by every repo and spent round-robin once every repo has listed (`countHotIssues`): round k counts each repo's k-th candidate, all repos in parallel, the higher total first, so the repos that list longest (Codex, Claude Code) still get their turns; a candidate past the cap is skipped, and a failed count gives back the calls it did not make. Each hot issue sent to the prompt gets one fix-status call (`fetchFixStatus`: the timeline's first 100 events, a same-repo PR that cross-references it with a closing keyword; merged beats open), at most `HOT_ISSUE_MAX_STATUS_CALLS` (66) per run; the row shows "fix PR #N open" or "fix #N merged", and a failed lookup shows nothing and keeps the issue. The run logs `[github] hot issues: N list pages, M count calls, K fix-status calls` (and the skips). Worst case per daily run: 33 repos × 8 list pages + 250 count calls + 66 fix-status calls + 33 repos × 5 release pages = 745 core calls, retries of a 5xx, a truncated body or a timeout (at most 2 per request) on top, against the Actions `GITHUB_TOKEN`'s 1,000 an hour (the weekly run's star-history calls come on top, and a major release's announcement page is fetched outside the GitHub API); a normal day lists one page for most repos. An issue updated in the last 2 days has a baseline and costs a count call only when its gain clears the bar (the recount above). Hot issues use no search call. A failed gain fetch skips that issue. A closed issue is never sent. A hot issue is shown once: one an earlier day showed (`digests/hot-issues-state.json`, id `issue:<owner/repo>#<n>`, saved after the LLM health gate for the agents page and a published data report) is left out, its slot freed, however much engagement or which labels it gains. The state is never pruned (`nextHotIssuesState`), so an issue is shown once, ever; it grows by a few ids a day. A failed hot-issue fetch degrades to none and never discards the releases.
- **News**: `matchProjectNews` matches a story's title and description, and drops an item naming 3+ agents (a compatibility list, not news); the prompt gets the description too. A GitHub repo is news only as the project's own repo on GitHub Trending.
- One LLM call per section writes one `## <Project>` per active project; the prompts forbid stating absences. Code decides what shows: a project section needs a bullet, text outside a `## <Project>` section is dropped, and a project with a stable release the model left without a bullet gets a code-written section with a Release line (`releaseFallbackSection`: the release link and its first 3 non-routine note items), and one whose section names neither a `**Release:**` bullet nor a release tag gets that line appended. Quiet projects go in one line, a project the model left out included; a project whose release fetch failed goes in an `**Unavailable today:**` line, so "shipped nothing" and "could not be checked" read differently.

### Data engineering (`ai-data`)

- **Audience**: data engineers at Digital Power (`.scratch/data-watch/spec.md`).
- **Repos**: `databricks`, `snowflake` and `data_stack` in `config.yml`, on the agents' pipeline. News matching is a pool of its own with no names-per-item limit: a story naming DuckDB, Polars and Iceberg is stack news. The two pools claim links apart, so one article can be news on both AI Agents and Data Engineering, on purpose: colleagues read Data only (placement rules: `.scratch/digest-structure/spec.md`). A name that is an ordinary word has `keywords`, and repos checked and left out are listed, as comments in `config.yml`.
- **Releases this week**: the data repos' stable releases of the last 7 days that no earlier report showed (`release:<owner/repo>@<tag>` in the data state's `reported`), so a release shows once; one from the last 24h is left to its repo section. Widening the repo sections' window instead would repeat a release on seven consecutive days.
- **Vendor feeds**: `data.feeds` in `config.yml` (spike: `.scratch/data-watch/issues/01-feed-spike.md`): the Azure Databricks release notes (rather than AWS: clients are mainly on Azure), the Fabric blog and Azure updates (filtered by `categories`), Snowflake's release notes and behavior-change bundles, BigQuery's Atom feed. The vendor blogs are not sources: their product posts repeat the release notes.
  - **State key**: title + date (Databricks lists a note under two guids), or the guid on a `stable_id: true` feed. A note that ships what a coming-soon note announced is skipped (`shippedComingSoon`). An item without a stage dated over 7 days before the run is dropped. A BigQuery note's verdict id stays `<anchor>#<type>: <first sentence>`, its title before 2026-10-28.
  - **Description**: a vendor item's plain text cut at 1,000 characters (`vendorText`), opened by the post's `<h2>`–`<h4>` headings (`Sections: …`), so Jev and the summaries see every feature of a multi-feature post.
  - **Relevance**: `selectVendorItems` (`src/data/relevance.ts`; weights in `dataRelevance`). A significance score under confidence 0.4 (`LOW_CONFIDENCE`, shared with AI Policy) counts as unknown: level 1 ("Notable") in the relevance score. An item naming a Tracked data project, or known to be at least "Notable" (not unknown), is kept on a real change of 0.4. A section with no kept item takes its best item within 0.05 of the keep bar. Behavior-change bundles skip Jev: always kept, always a deprecation. At most `MAX_VENDOR_ITEMS` with per-section floors (`SECTION_FLOORS`); deprecations are never cut. A kept non-deprecation whose significance is under level 1 ("Notable") or unknown is `minor`: in its table, never a Highlight (named to the prose call, and a Highlight bullet linking, naming or restating it is dropped in code: `dropNoHighlightRows`; when none is left the section reads `NO_HIGHLIGHT_NOTE`, which `highlights.json` does not restate). Kept items over the cap go in one `*Also new:*` line and are marked reported, so they do not come back (a coming-soon note excepted, so its GA note is not skipped).
  - **Action required**: every reported deprecation with an end date (Jev's `end_date` pick for a note, parsed from the page for a bundle), kept in the state's `actions` until the date passes.
  - **Tables**: per section, deprecations first, then newest first. The Item cell shows the title without the date Snowflake opens it with (`vendorTitleLabel`); a BigQuery title is its note's first sentence without the type prefix, plus the stage its text states, "(GA)" or "(Preview)" (`noteLabel`, `src/data/bigquery.ts`); ⚠️ for a deprecation, retirement or behavior change and 🤖 for an AI feature in a data platform (`aiInData`). A section whose rows all share one source has no Source column.
- **Layout**: `## Highlights` → `## Action required` → `## Databricks` → `## Snowflake` → `## Azure / Fabric & GCP` → `## Open-source stack` → `## Releases this week` → `## Across platforms` → `## Spotted` → `## EU data law` (`DATA_REPORT`). A Databricks, Snowflake, Azure / Fabric & GCP or Open-source stack section with nothing to show (no vendor row, no active or unavailable repo) has no heading: it is named in one "Nothing new from …" line after the sections, its quiet repos linked in brackets after its name, the only sign they are tracked (`namedWhenEmpty`, `nothingNew` in `src/core/strings.ts`). A section with vendor rows keeps its repos' quiet line. The prose call writes Highlights, then `## Across platforms` after `TABLES_MARKER` (left out when no capability moved on two platforms). EU data law is code only: links to today's kept AI Policy items that are EU data law (`isDataLaw`). Neither those links nor Spotted rows make a data report on their own.

### AI Models & Labs (`ai-models`)

- **Lab posts**: the Anthropic and OpenAI sitemaps, state `digests/labs-state.json`, saved whether or not the page is published. A post is new only when its URL is: `lastmod` moves for every URL. OpenAI's pages answer 403 to datacenter IPs, so its titles come from the URL slug, and a post without page text shows `—` and makes no Highlight: it is named to the Highlights call as no Highlight, and a Highlight about it is dropped in code (`dropNoHighlightRows`). A lab's first crawl gets one count line. Lab posts are not project news; a community story whose link is a listed lab post leaves Spotted.
- **New on OpenRouter**: catalog models created in the last 2 days that no earlier page listed (`digests/models-state.json`), from one daily catalog fetch (`fetchModelCatalogDaily`) shared with the stealth table.
- **Stealth models**: `isStealthModel`, rendered in code (`buildStealthSection`); with none listed, the page names them in its "Nothing new from …" line, like an empty Lab announcements or New on OpenRouter (`nothingNew`). 🆕 marks a model listed in the last `STEALTH_NEW_DAYS`; a 🆕 row alone publishes the page. If the cron is ever moved onto a stealth model, a ⏳ on that row means `OPENROUTER_MODEL` needs replacing.

### Trends (`ai-trends`, weekly)

- **Sources**: GitHub Trending (`since=weekly`; fetched daily with `since=daily` for agent news, whose detail names the window), the GitHub topic search (`SEARCH_TOPICS`, `NEW_REPO_MIN_STARS` for the Radar, `MIN_STARS` for the category tables), OpenRouter apps and rankings, npm registry search, Hugging Face, Claude Code Skills (`anthropics/skills`). OpenRouter has no usage API: the scrape of its RSC payload breaks silently when the frontend changes, so watch for `[openrouter] Parsed 0 apps` in the log.
- **Code ranks and renders the tables** (`composeTrendingReport`); the LLM writes only a row summary from the name and description (`summaryRows`: no stars, gains or ranks, which the row shows); code drops a later summary sentence made mostly of the first's words (`RESTATED_SENTENCE_SHARE`) and a trailing "in <language>" that repeats the Lang column (`tidyTrendsSummaries`). A category table picks up to 8 rows alternating the top by stars gained in 7 days with the top by relative gain (a cut row is `cap` in the trace) and shows them by stars gained; the gain is the trending page's figure, else the delta against `digests/trending-state.json` (star history read and written by the weekly run only), else the star history API (one call at a time, stopping at the first 403/422/429, capped at `MAX_STAR_HISTORY_CALLS`).
- **Legend and Models**: the Radar opens with a one-line legend (`radarLegend`: markers, inclusion order, units, windows). An OpenRouter or npm Signal shows its figure (tokens or downloads in the last 7 days) against the one the run dated exactly 7 days earlier saved for that row (`figures` in `digests/trending-state.json`, the shown rows only): "vs previous week", none when the row was not on that page. OpenRouter usage is a code table (`renderOpenRouterUsage`): rank, the model linked, one day's tokens from the rankings snapshot, and with last week's saved ranking (`modelRanking`) a Last week column: its rank then, or "new". A 🆕 OpenRouter app with neither description nor usage gets no row; one without a description borrows its GitHub repo's when the trending page or topic search has it, and a shown Radar row still without one its site's meta description (`withSiteDescriptions`, `src/trending/compose.ts`); a `.local` or `localhost` origin gets no link (`publicUrl`). The Hugging Face table is code too (`renderHfTable`): the Hub's order by likes gained in 7 days (`#`), total likes, downloads in the last 30 days, 🔥 by the `hf:<id>` keys saved in `reported`, one row per release (`hfReleaseRows`: uncensored re-uploads left out, quantised copies linked on the original's row). The LLM writes only its summaries, from task, parameter count and license, never a tag; without one the row shows its task and size. A Radar, category or Hugging Face row that shows "—" (no summary, no description) is named to the prose call as no Highlight (`unsummarizedRows`), and a Highlight about it is dropped in code (`dropNoHighlightRows`), as the data report does with `minor` rows and the models page with lab posts without page text.
- **Markers**: 🆕 means new only (a repo created, an OpenRouter app listed, in the last 14 days; `GLOSSARY.md`), never momentum. 🔥 marks a row also in the report dated exactly 7 days earlier. Each agents table's heading carries its category's emoji (`TRENDS_REPORT.categoryTitles`, 🚀 for the Radar). A 🔥 GitHub repo in no `config.yml` section is listed under Candidates to track, linked, by the section its Jev category fits (`coding_agent` → `agents`, `agent_tooling` → `infra`, any other → "No matching section"), with its config lines collapsed below; nothing joins a section without a config edit.
- **Scope**: Jev decides scope and category (`classifyTrendingItems`); a Radar row needs `standalone_tool`. OpenRouter apps tagged `cli-agent`, `ide-extension`, `cloud-agent` or `personal-agent` skip Jev: most have no description.
- **Skills: PRs and requests this week** (`src/trending/skills.ts`): the `anthropics/skills` PRs and issues updated in the last 7 days, a closed issue only if it closed in those 7 days and a closed PR only if it was merged in them (`merged_at`, from the pulls response): a PR closed without merging is left out, so the section shows only open, merged and requested work, and its Takeaway rests on those. One the Skills section of the page dated exactly 7 days earlier named is skipped unless it closed (a PR: merged) this week. An item whose title names none of the audience terms (`AUDIENCE_TITLE_RE`: the developer skills, evals and triggering, skill distribution, Claude Code sessions, hooks, memory) is dropped in code, so games, blockchain, media and the document-format skills (docx, pptx) stay out; the prompt's off-audience rule stays as a second net for a kept title whose item is off-audience. No item: no section and no call.
- **Signals and Highlights**: the prose call gets a facts block computed in code from the rendered rows (`trendsFacts`, `src/trending/facts.ts`): per table the largest absolute and relative star gain, each Radar source's leader, OpenRouter's #1 and provider counts within the top 10, Hugging Face's Likes and Downloads as totals; the fact sentences are `TRENDS_FACTS` (`src/core/strings.ts`). Comparisons ("largest", counts, shares) come only from it; a Signal (each list item or paragraph under Signals; a sub-heading is kept) without a link is dropped while a linked one remains, and a Highlight without one is logged (`checkTrendsLinks`).
- **Research**: the 10 most relevant papers that the daily ArXiv ranking saved in `digests/research-state.json` in the 7 days before the run (`digests/arxiv-state.json` holds the fetch cutoff). A paper applying LLMs or agents to one field outside software and data engineering (Jev's `domain_application`) loses up to `DOMAIN_APPLICATION_PENALTY` (20%) of its relevance; a trace row without that answer gets no penalty. **Most discussed**: the week's stories from the Spotted log that no page showed.

### AI Policy (`ai-policy`)

- **Scope**: AI legislation, regulation and official guidance, ~95% EU, the Netherlands and the US (`.scratch/ai-policy/spec.md`), for the reader in `policy.reader_profile`.
- **Sources**: RSS feeds in `policy.feeds` (each with its `jurisdiction`; `kind: news` for the News & commentary outlets; `jev_only` for feeds whose relevant items need not name AI), and the non-RSS sources in `POLICY_SOURCES` (`src/policy/sources.ts`): a new source is one module, one line there and its config. A failing source is logged and skipped; the report is skipped only when all fail. The Commission mail source (`policy/commission-mail.ts`) reads every inbox on `AGENTMAIL_API_KEY`: the digital-strategy RSS feed is a curated subset of the site, so a site page takes the feed's Drupal guid as its id (`<node> at https://digital-strategy.ec.europa.eu`), and `fetchPolicyData` keeps one item per id. The digital-strategy site answers HTTP 403 to GitHub's runners (its RSS feed on every run from 2026-10-22 to 10-26, and the mail's redirect links), so on CI the RSS feed gets nothing and a mail item keeps the mail's title under the site's redirect for its newsroom item (`https://digital-strategy.ec.europa.eu/news-redirect/<item>`) as id and link, which a browser follows to the page. An item that resolves one night and not another is reported twice (accepted, 2026-10-27: on CI it never resolves). Open States answers on CI (2 items a day on 2026-10-25 and 10-26); its search noise and free-tier limit are unverified.
- **Quiet sources**: a primary source (a registered source, or a feed without `kind: news`) with no judged item for `QUIET_SOURCE_WARN_DAYS` (7) days running logs `[policy] WARN <source>` and notes it in `$GITHUB_STEP_SUMMARY`; a failed fetch counts as quiet. The first quiet day per source is `zeroSince` in `digests/policy-state.json`.
- **Watchlist** (`policy.watchlist`, per jurisdiction): act numbers, procedures, dossiers, dockets, RINs and bills. European Parliament procedures and Dutch bills are found only through it (the EP discovery feed answers HTTP 500; Dutch AI bills are named after the EU regulation, so no keyword finds them): add new ones there. A non-news item naming an entry of its jurisdiction's list is always kept.
- **Relevance**: `selectPolicyItems` (`src/policy/relevance.ts`; weights in `policyRelevance`); US items also need an impact on the reader; an impact score under confidence 0.4 counts as unknown, so a notable item (significance level 1 or more) keeps it. Only kept items enter the state, so a dropped item is checked again the next day, from its saved verdict.
- Code renders the tables (one per jurisdiction, News & commentary, Coming up); the LLM writes only row summaries and Highlights, so a legal status or date never comes from the model. A summary sentence about the model's input ("the provided text does not …") is dropped and logged (`dropInputTalk`), and a row without a stage shows `—`.
- **Coming up**: the open deadlines of reported items plus `policy.calendar`, the next 30 days.
- **EU data law**: `policy.data_law` lists the tokens that mark a kept item as EU data law, linked from the data report.

### Community and Spotted

- **Sources**: HN's top 500 filtered by AI and data keywords (`src/sources/hn.ts`), Dev.to (`DEVTO_MIN_REACTIONS`), Lobste.rs (`ai`, `vibecoding`, `databases`). A story's description is its page's meta description (Lobste.rs: the submitter's text first; Dev.to: the article's own). `cleanStoryDescription` strips page boilerplate (GitHub's "Contribute to …" and " - owner/repo", subscribe lines, a trailing "..."). The summaries are in the model's own words with one concrete fact; a row linking a GitHub repo shows the repo as its link text. The model sees titles, counts and descriptions, never the article or the thread: a row without a description gets `—`, and the prompts forbid describing comment threads.
- **Spotted**: the fresh stories (no page showed them on an earlier day, by id or `linkKey`; plus yesterday's stories the per-source cap alone cut, `cut` in the log, which the sources no longer return: `carriedStories`) that no project news or listed lab post took, routed by Jev to a topic; `PAGE_OF_TOPIC` maps it to a page; policy and other have none: policy stories with at least `POLICY_TALK_MIN_POINTS` (top `POLICY_TALK_PER_SOURCE` per source) go in the Overview's "Policy talk" list, then other stories with at least `TALKED_ABOUT_MIN_POINTS` (top `TALKED_ABOUT_PER_SOURCE` per source) in its "Also talked about" list, both in `talked-about.json` (split by `topic`), and count as shown. The two lists do not compete for slots; a link in both goes to policy. Each link is shown once. A story needs a topic probability of `SPOTTED_MIN_TOPIC_PROBABILITY` (0.6) or more, is at most `SPOTTED_MAX_AGE_DAYS` (7) old and is no Dev.to contest entry; once a page has 3 rows, a further row needs `SPOTTED_MIN_POINTS` of its source. At most `SPOTTED_PER_SOURCE` rows per source and page, each source ranked by topic probability (in tenths), then points, with no combined score: points, scores and reactions are not comparable.
- **Log** `digests/spotted-log.json`: every fetched story with its latest counts and `shown`, saved after the LLM health gate, pruned after 8 days. Trends' Most discussed reads it: a row needs `MOST_DISCUSSED_MIN_COMMENTS` of its source and a topic other than `other` (from `spotted-verdicts.json`).

## Key conventions

- Fixed report strings live in `src/core/strings.ts`. `config.yml` holds each repo section's `title` (its heading) and `subject` (the LLM's wording), so re-scoping a section is a config edit plus `pnpm readme`. Reports are English-only: one file, one GitHub issue per report.
- Item lists are Markdown tables rendered in code; the LLM writes only the row summaries (`src/reports/summarized-table.ts`). Every backticked token in a data, models or policy summary is checked against its row's source, and in a repo section's `## <Project>` bullets (agents and data report) against that project's block in the prompt (`checkCodeTokens`): a respelled identifier takes the source's spelling, an unknown one loses its backticks. A failed summaries call shows the descriptions; a failed prose call leaves `MSG.summaryFailed`, except on AI Policy, which is then not written.
- Page layout: `## Highlights` → the tracked sections → `## Spotted` (→ Coming up). Highlights pick 1–3 bullets, one subject each, and `highlights.json` restates only those Highlights, leading each report with its page's first bullet; a models page without a lab post or new model says so (`NO_MODEL_NEWS_NOTE`). Daily pages have no Signals or Worth a Look; Signals, on Trends, is the one place for trend claims. Prompts give the exact `##` headings and forbid a title (`NO_TITLE_RULE`); `stripModelTitle`, `unwrapCodeLinks` and `nestHeadings` clean up what models write anyway. Under the report bar every page has one meta line: its counts, then `Generated:` (`REPORT_META.line`). A repo-section bullet's label is written `**Release:**`, colon inside (`boldLabelColonInside`), whichever form the model wrote.
- Retired reports (`ai-weekly`, `ai-monthly`, `ai-cli`, `ai-ph` and the October 2026 merges) stay in `REPORT_LABELS` only so their archive stays reachable: do not add generation code back. `REPORT_LABELS` titles stay cadence-neutral because the archive holds both daily and weekly reports.
- A weekly report gates its fetch and save on `isWeeklyRun`; `WEEKLY_REPORT_IDS` is the one list of weekly reports.
- `callLlm` defaults to 8192 tokens; the listing calls use `LLM_TOKENS_LISTING` (16384), gpt-4o's output cap (the OpenAI and Copilot default model), so a higher budget would break those providers. Reasoning tokens count against the same budget.
- `callLlm` retries 429s, connection failures, an unavailable model, and empty or cut-off answers, each on its own ladder (`src/core/llm.ts`), and releases its concurrency slot during every wait. Do not bypass the limiter by calling SDK clients directly.
- **LLM health gate**: `assertLlmHealthy` throws when at least `LLM_MIN_SAMPLES` calls ran and at least half failed. `main()` calls it after every report is built and before the reports are written, so a provider outage exits non-zero with nothing committed, no issues opened and no Telegram message sent (a local run still changes the state files the builders saved): a missing day is recoverable by `workflow_dispatch`, a published day of placeholders is not. `reportLlmHealth()` notes lost calls in `$GITHUB_STEP_SUMMARY`.
- **Providers** (`src/providers/`): the factory logs only the provider name, never API keys or endpoint URLs. The daily run uses OpenRouter with a free model, fallbacks and `OPENROUTER_REASONING_EFFORT=low`, set in `.github/workflows/daily-digest.yml`; without the low effort a reasoning model spends the whole budget on reasoning and returns empty content. Free models can go down without notice: when the fallbacks fail too, the health gate aborts the run, and the fix is a new `OPENROUTER_MODEL` (`/api/v1/models/<id>/endpoints` shows each endpoint's uptime).
- **One digest per CST day**: the workflow's `concurrency: daily-digest` group serializes overlapping runs, and its `guard` job skips a scheduled run whose `digests/YYYY-MM-DD` folder is already committed. `workflow_dispatch` always proceeds: that is how a day is regenerated.
- `pnpm close-stale` (`closeSupersededIssues`) keeps the newest open digest day's issues per retention group (the daily labels together, each weekly label alone) and closes the rest, so a failed run leaves yesterday's reports up. A retired report's label goes in `DIGEST_ISSUE_LABELS` so its last issue still closes. Pull requests are excluded.
- **Teams**: `pnpm notify` also posts the data report's highlights to a Teams channel through a Power Automate Workflows webhook (`TEAMS_WEBHOOK_URL`); unset, it skips silently; a failed post is logged and never fails the run. Point the secret at a private test channel before the team channel.
- A new GitHub issue label gets its color in `LABEL_COLORS` (`src/core/github.ts`).

## Web UI & RSS Feed

- `index.html` reads `manifest.json` (`pnpm manifest`, `src/cli/manifest.ts`) to build the sidebar and fetches `digests/YYYY-MM-DD/<report>.md` on demand. `#YYYY-MM-DD` is the day's overview (each report's highlights, then Policy talk and Also talked about from `talked-about.json`, then Coming up from `coming-up.json`); `#YYYY-MM-DD/<report>` is a report. The sidebar pins the latest weekly reports under "This week" (manifest `weekly`) and tags the newest day `today` (`latest` when it is not the viewer's own date).
- Each report's bar is rendered in code with absolute Pages URLs, so its links work in GitHub Issues too.
- The Markdown carries no `+`: Highlights are plain bullets, and a bullet about something going away opens with `GOING_AWAY` (−). From `SIGNED_SINCE` on, the web UI alone renders Highlights as a diff hunk (`gutterList`): − for a bullet that opens with `GOING_AWAY` (the sign removed from its text), + for the rest. No code checks the model's sign: a keyword rule would sign a release with breaking changes as going away. AI Policy's Highlights are prose, so its page has no gutter.
- The look is "Gutter": the mark is a diff gutter (+ over −), drawn into `favicon.svg`, `favicon-16.svg` and the PNGs (`apple-touch-icon.png`, `feed-icon.png`, `og-image.png`, `banner.png`). IBM Plex Sans, Plex Mono for dates, counts and code. Green and red mean added and going away, and nothing else.
- The Markdown keeps ISO dates, for GitHub Issues, RSS and the MCP server; `decorateReport` formats them in the web UI and stacks tables of 3+ columns on a phone, with the `PROSE_COLUMNS` at full width.
- MCP server: `mcp/`, a Cloudflare Worker that reads the reports from GitHub Pages, so new digests need no deploy. `.github/workflows/deploy-mcp.yml` deploys it on pushes to `main` that touch `mcp/`. `mcp/` has its own `package.json`; run `pnpm run deploy` there, not `pnpm deploy` (pnpm's workspace command).
- RSS: `feed.xml` (the latest 30 items across reports) and one `feeds/<id>.xml` per live report, from `pnpm manifest`.
- The daily workflow commits the digest, then the manifest and feeds, and pushes once: two pushes seconds apart make Pages cancel the first build.

## Adding a new report type

1. Create a data fetcher (or add to an existing one). For a repo-backed report, add its key to `SECTION_KEYS` in `src/core/config.ts`: that loads it as a `SectionConfig` (`title`, `subject`, `repos`) and lists it in README.md, which then needs a `<!-- tracked:<key> -->` … `<!-- /tracked:<key> -->` marker pair (`pnpm readme` fills it in). Its prompt wording comes from `PROJECT_SCOPE` (`src/core/strings.ts`) and its `subject`. Any other `config.yml` key needs its own `RawConfig`/`RadarConfig`/`loadConfig` entry: a section with no schema entry is silently ignored. Decide daily vs weekly: a weekly report gates its fetch and save on `isWeeklyRun`, and its id goes in `WEEKLY_REPORT_IDS`.
2. Add a `buildXxxPrompt` function in `src/reports/prompts-pages.ts` (page prompts) or `src/reports/prompts.ts` (repo-level prompts).
3. Add its square emoji and matching color, name and issue label to `REPORTS` in `src/core/strings.ts` (a square no other report uses, never green or red; the name cadence-neutral: no "daily"/"weekly"); the H1, issue title and labels derive from it.
4. Add a `buildXxxReport` function in `src/reports/pages.ts` that returns a `SavedReport` and makes the report's LLM calls.
5. Wire it into `fetchAllData` and the save phase in `src/index.ts`. The fetcher never throws: it catches its own failure and returns its empty value (`fetchSuccess: false`).
6. Add a label color entry in `LABEL_COLORS` in `src/core/github.ts`.
7. When retiring a report, move its id and label into the archive part of `REPORT_LABELS` (`src/core/strings.ts`; `REPORT_FILES` in `src/cli/manifest.ts` is its keys), add its issue label to `DIGEST_ISSUE_LABELS` (`src/core/github.ts`), and add its id to the archive list in `get_report`'s type description in `mcp/src/index.ts`.
8. Update README.md and this file.
