# AGENTS.md

## Project overview

Daily Diff is a daily digest generator for the AI open-source ecosystem. A GitHub Actions cron job is set for 01:07 Europe/Amsterdam (GitHub starts it 2.5–4 h late, so the digest lands by about 05:00 Amsterdam time) and produces English reports, published as GitHub Issues and committed Markdown files. Most reports are daily; a weekly set runs on Mondays (CST).

## Commands

```bash
pnpm start          # run the full digest locally
pnpm test           # vitest (unit tests)
pnpm typecheck      # tsc --noEmit
pnpm lint           # ESLint
pnpm lint:fix       # ESLint --fix
pnpm format         # Prettier --write src
pnpm format:check   # Prettier --check src
pnpm readme         # regenerate README's tracked-repo tables from config.yml (--check: fail if stale)
```

Required env vars for local runs:

```bash
export GITHUB_TOKEN=ghp_xxxxx
export DIGEST_REPO=owner/repo   # omit to skip GitHub issue creation

# LLM provider (default: anthropic)
export LLM_PROVIDER=anthropic   # anthropic | openai | github-copilot | openrouter | deepseek | qwen

# Anthropic (default)
export ANTHROPIC_API_KEY=sk-ant-xxxxx

# OpenRouter
# export OPENROUTER_API_KEY=sk-or-xxxxx

# DeepSeek
# export DEEPSEEK_API_KEY=sk-xxxxx

# Jev: ArXiv relevance ranking, trending scope and cross-source matching
# (omit: ArXiv ranks by recency, trending falls back to search topic labels)
# export TYPESAFE_API_KEY=xxxxx

# Run the weekly reports (trending, models) and the Dev.to/Lobste.rs sections on a non-Monday
# export DIGEST_FORCE_WEEKLY=1
```

## Architecture

The pipeline runs in four sequential phases, each implemented as a named async function in `src/index.ts`:

1. **`fetchAllData`** — all network I/O in parallel. Daily: releases + hot issues for the `agents` and `infra` repos in `config.yml`, Anthropic/OpenAI sitemaps, GitHub Trending (HTML + Search API, for agent news), Hacker News Firebase API, ArXiv API, OpenRouter model catalog (stealth models). Weekly only (`isWeeklyRun`): Claude Code Skills, OpenRouter apps/rankings, npm registry search, Hugging Face Hub API, Dev.to Forem API, Lobste.rs JSON API. The weekly trending fetch also ranks and selects the report's rows (`composeTrendingReport`).
2. **News matching** — `matchProjectNews` (`src/agent-news.ts`) assigns HN, web and trending items to the agents and infra projects they name.
3. **`generateSummaries`** — one LLM call per section of the agents report (agents, infra); on the weekly run also skills, and two for trending (row summaries and prose). Rate-limited to 5 concurrent requests by a queue in `src/report.ts`.
4. **Save phase** — `buildProjectReportContent` (in `src/report-builders.ts`) builds the agents report, one section per config group; the `buildXxxReport` functions (in `src/data-reports.ts`) make the LLM call and return the other reports. Once every report is in, `main()` adds each one's report bar (`renderReportBar`: links to the day's overview and other reports), writes the files, generates `highlights.json` and opens the GitHub Issues.

## Tracked sources

- **Agents** (daily): `agents.repos` in `config.yml`, the only list (README's table is generated from it). On 2026-10-10 Qwen Code, OpenClaw, IronClaw, QwenPaw, ZeroClaw and Copilot CLI were dropped (unused by the maintainer); Kilo Code, Oh My Pi, jcode, Cline, Command Code and DeepSeek Harness were added. Per-repo quirks (no releases, issues disabled, prerelease-only) are comments next to the entry in `config.yml`. One list, CLI or not — the CLI/OpenClaw split was merged in October 2026. Optional `keywords` per agent set the news-match terms (Pi needs them: "pi" alone matches Raspberry Pi).
- **Infra** (daily, a section of `ai-agents`): `infra.repos` in `config.yml` — agent tooling since 2026-10-10 (sandbox, session multiplexers, context tool), with news matching like the agents. A weekly report of its own until October 2026, which mostly listed quiet projects. Until 2026-10-10 the section tracked inference engines (vllm, sglang, llama-cpp, ollama, litellm, unsloth); the `ai-infra` archive label stays "AI Infrastructure Digest". The section heading is `infra.title`.
- **CLAUDE_SKILLS_REPO** (weekly, in `ai-trending`): anthropics/skills — no date filter, sorted by popularity
- **Web**: anthropic.com + openai.com via sitemap, state in `digests/web-state.json`
- **Trending**: github.com/trending (HTML) + GitHub Search API over 6 agent topics (`SEARCH_TOPICS`: `coding-agent`, `agentic-coding`, `ai-coding`, `agent-harness`, `harness`, `agent-orchestration`). Fetched daily for agent news (top 15 pushed in 7 days per topic); the report is weekly and scrapes `since=weekly` that day. The weekly run searches each topic twice, 100 per page: repos _created_ in 14 days with 25+ stars, and every repo pushed in 7 days with 100+ stars (up to 3 pages) — 16 requests, 565 unique repos on 2026-10-07. Sorted by total stars, the pushed query alone was an all-time leaderboard, top 15 per topic; `ai-agent` and `multi-agent` were dropped that day (stock bots, slide generators, RAG apps). It also adds OpenRouter and npm; with the new repos these feed an "Agent & Coding Tool Radar" section of standalone agents and coding tools worth watching.
  - **Code renders the tables** (`composeTrendingReport`, `src/trending-rank.ts`); the LLM writes only a 2-sentence summary per numbered row (`N: text` lines) and the prose around the tables, which it marks with `<!-- tables -->`. A missing summary line shows the description, truncated; a missing marker puts the tables after the prose. The old single prompt chose scope, category, order and 🆕 itself, and topic-search repos had no momentum figure at all.
  - GitHub rows are sorted by the stars gained in the last 7 days, from the first source that has it: the trending page's weekly gain, the delta against the star-history point from exactly 7 days ago, every star of a repo created less than 7 days ago, else `GET /repos/{o}/{r}/stargazers/history` (`fetchWeeklyStarGain`), else none (sorted after the rest, by total stars). The relative gain is the gain over the stars a week ago, only when that baseline is 100+ (`RELATIVE_MIN_BASELINE`), else 8 → 16 stars reads as +100%. Cells read `12,345 (+812, +7.1%)`.
  - The star history API returns weekly buckets of daily star counts that sum to `stargazers_count`, so the gain is exact; `per_page=2` covers 7 days from any weekday. `composeTrendingReport` asks it only for rows still without a gain that could reach the report (established repos in scope, new repos with 25+ stars that pass `onRadar`), so it classifies before it fetches: a verdict is saved, a gain is not. Calls run one at a time (the endpoint answers 422 when "spammed"), stop at the first 403/422/429, and are capped at 500 (`MAX_STAR_HISTORY_CALLS`): the Actions `GITHUB_TOKEN` allows 1,000 core requests an hour per repository and the rest of the run makes ~60–80. The stargazer list endpoints no longer work (REST 404, GraphQL empty, 2026-10-07).
  - `digests/trending-state.json` (committed, like `web-state.json` and `arxiv-state.json`) is the star history that saves those calls: `[CST date, total stars]` per GitHub repo, recorded on every weekly run. Only a point exactly 7 days old is read, so a forced mid-week run cannot shorten next Monday's window; points older than 7 days are pruned. Repos missing from a run are carried forward. Only the weekly run reads and writes it, after the report is saved; a same-day re-run computes the same deltas. The first run, and one after a missed Monday, fetches every gain from the API instead (up to the cap, ~2–3 minutes).
  - The category tables hold established repos only, at most 8 per category, alternating the top by absolute gain with the top by relative gain (`interleaveGains`): the biggest movers and the fastest-growing smaller repos, with no combined score. A relative pick needs a gain of at least 50 stars (`RELATIVE_MIN_GAIN`): on the 2026-10-08 live check a +22-star week (138 stars, +19%) took a multi-agent slot. A new repo (created in 14 days) goes to the Radar instead, by absolute gain, and only with at least 25 stars: on the 2026-10-06 live check an 8-star repo created that day ranked above week-old repos.
  - The Radar orders 🆕 first, then each row's relative position in its own source list (ranks, stars and download ratios are not comparable, so no combined score). Rows that share a GitHub repo or a site-root host merge into one. At most 8 of its 12 rows are 🆕, and at most 20 of the 30-row merge pool: about 45 new GitHub repos a week otherwise crowd out Hermes, Kilo Code and Cline.
  - Jev decides scope and category (`classifyItems`, `src/trending-jev.ts`): one request per item it has not judged before (about 650–750 on the first run with the 565-repo search pool, then only new items), with a `category` Choice (five categories plus `out_of_scope`) and a `standalone_tool` Noul. A Radar row needs `standalone_tool` ≥ 0.5, so plugins, MCP servers and proxies can still reach the category tables but not the Radar. OpenRouter apps that OpenRouter tags `cli-agent`, `ide-extension`, `cloud-agent` or `personal-agent` skip Jev and count as in scope: most have no description, and on the 2026-10-07 live check Jev put 14 of 37 tagged apps (goose, Crush, Command Code…) out of scope from the bare name. Untagged apps, and those tagged only `programming-app` or `native-app-builder` (which also covers gateways and game engines), are still judged. Without `TYPESAFE_API_KEY`, or when more than half the calls fail, the search topic label decides for the items not in the cache (`fallbackClassification`), and a trending-page repo that no topic search returned is dropped.
  - `digests/trending-classifications.json` (committed) caches Jev's verdict per item key (GitHub keys lowercased), one item per line, so each item is asked once instead of every week: a project's scope does not change. An item is asked again only when its description changes (`desc` is a hash of the one Jev read), so a new repo first seen with an empty or placeholder description is not out of scope for good. Saved verdicts are used even without a key or when the new calls fail. Only Jev answers are saved, never a topic-label fallback or a tagged OpenRouter app, and an agent tag beats a verdict saved before the app was tagged. **To fix a verdict**, edit `category`/`standalone` and delete `desc` so a description change does not undo it; to have Jev ask again, delete the entry. A file that fails to parse means every item is asked and the file is left as it is. Items unseen for 180 days are pruned.
  - `digests/trending-matches.json` (committed, like `web-state.json`) holds Jev's cross-source matches: OpenRouter app id → its npm package and GitHub repo, plus the candidates it `rejected`. Code can't match on names (`pi` also matches the plugins `pi-acp` and `pi-mcp-adapter`), and an OpenRouter app's URL rarely shares a host with its npm or GitHub links, so Jev decides each pair once and later runs reuse the answer. A pick below 0.8 probability rejects every candidate offered. Code never overwrites a match. **To fix a wrong match**, delete its `npm` or `github` field and add the key (`npm:<name>` or `github:<owner/repo>`) to `rejected`; to force one, set the field. A file that fails to parse turns matching off for that run and is left as it is. Rejections outside the current pool and apps unseen for 180 days are pruned.
  - `digests/YYYY-MM-DD/trending-ranking.json` traces every classified item (category probabilities, noul, gain, its source and relative gain; a saved verdict shows the `decided` date instead of probabilities, which are in that day's trace) and every match decision, so a misplaced repo can be traced without rerunning Jev. Not a report and not in `REPORT_FILES`.
  - **OpenRouter** has no usage API. `/apps` and `/rankings` embed their data in the Next.js RSC payload (`self.__next_f.push` chunks), parsed by `extractRscPayload` + `extractJsonArray`. `/apps` carries the top 200 apps for day/week/month plus a `trending` list with `growthPercent`; category pages load client-side, so apps outside those lists are invisible. The scrape breaks silently when the frontend changes — watch for `[openrouter] Parsed 0 apps` in the log.
  - **npm** uses the `downloads.weekly`/`monthly` already in the registry search response (the downloads API rejects scoped packages in bulk). Counts are gameable and the keywords match plugins/MCP servers too; the prompt tells the LLM to filter those.
- **Stealth models** (daily, top of `ai-agents`): `isStealthModel` matches a `stealth/` id prefix, or a description saying "cloaked"/"anonymous"/"stealth" … "model", in the official `/api/v1/models` catalog. `buildStealthSection` (`src/report-builders.ts`) renders it deterministically — not by the LLM — via the `preamble` of `buildProjectReportContent`. It always appears: 🆕 = listed within 2 days, ⏳ = `expiration_date` within 3 days, and "catalog unavailable" is distinct from "none listed". If the cron is ever moved back onto a stealth model, a ⏳ on that row means `OPENROUTER_MODEL` needs replacing.
- **HN**: Firebase API (`/v0/topstories.json`) — scans top 500 stories in batches of 50, filters for AI keywords, top 30 by points. The model sees titles and counts only, so the prompt forbids describing comment threads; before 2026-10-06 it asked for "the community's typical reaction" and every summary made one up.
- **ArXiv**: ArXiv API (Atom XML) — cs.AI, cs.CL, cs.LG sorted by submission date, paged 300 at a time (max 4 pages per category) back to the newest paper the previous run saw — `digests/arxiv-state.json`, written only once the report is built, committed like `web-state.json`; a same-day re-run reuses the previous cutoff, and with no state it falls back to 48h — then ranked by relevance with TypeSafe's Jev (`POST api.typesafe.ai/v1/systemone`, one request per paper, `TYPESAFE_API_KEY`); the request asks five atomic questions — how central LLMs are (score, 0–2: a paper can be partly about LLMs, which a noul near 0.5 can't express), and nouls for agents/tool use/code, proposes a technique, works without training, results on widely used models — and `relevanceOf` weighs them in code: 0.5 LLM centrality, 0.2 agents, 0.1 widely used models, 0.1 for technique × without training (the second only means something when there is a technique) with 0.1 more for a code link in the abstract (`hasCodeLink`, a regex) — TypeSafe's composite-scoring pattern. The topic nouls alone left about one paper in six tied near the top score; the other three spread that group out. The raw answers for the top 100 papers and the model version go to `digests/YYYY-MM-DD/arxiv-ranking.json` (one paper per line, ~30 KB), so a misranked paper can be traced and the weights retuned without rerunning Jev; it is not a report and is not in `REPORT_FILES`; the top 40 go to the prompt with full abstracts. Jev is not a chat model, so it bypasses `callLlm` and `llmStats`. No key, or more than half the scoring calls failing, falls back to the 40 most recent. The state replaced a fixed 48h window from the run time: arXiv announces Sun–Thu at 20:00 ET with submissions up to 14:00 ET the day before, so the nightly run only sees papers more than a day old. The window skipped the Tuesday (CST) report every week, never showed the Thursday–Friday batch, and clipped the first ~4.5h of every other batch. There is still no ArXiv report on days when arXiv announced nothing since the previous run: Sunday and Monday (CST) with the cron at 22:37 UTC; the 2026-10-11 move to 01:07 Amsterdam time can shift those days. Before October 2026 the report took the newest 50, a few hours of submissions.
- **Dev.to and Lobste.rs** (weekly, in `ai-hn`): Dev.to (5 AI tags, top of the week) + Lobste.rs (`/t/ai.json`, `/t/ml.json`, last 7 days). The separate weekly community report was folded into the discussions report in October 2026; `buildDiscussionsPrompt` asks for their sections only when they were fetched, and the report is still written when HN fails.
- **Models** (weekly, `ai-hf`): Hugging Face Hub trending models plus OpenRouter token usage and newly listed models (`buildModelUsageData`), which were the trending report's "Model Usage on OpenRouter" until October 2026. HF is weekly because the Hub list is ranked by cumulative downloads and 90.5% of a day's models carried over from the previous day, so daily generation was re-summarizing the same table.

## Key conventions

- All fixed report strings (report names, labels, headings, footers, messages) are centralized in `src/i18n.ts`. `config.yml` holds each agents-report section's `title` (its heading) and `subject` (the LLM's wording), so re-scoping a section is a config edit plus `pnpm readme`. Reports are English-only: one file, one GitHub issue per report.
- LLM prompt builders are split across two files: `src/prompts.ts` (repo-level prompts) and `src/prompts-data.ts` (data-source prompts). Each report type has its own builder function.
- Weekly and monthly rollups were removed in July 2026. `ai-weekly`/`ai-monthly` remain in `REPORT_LABELS` (`src/i18n.ts`) and `REPORT_FILES` (`src/generate-manifest.ts`) only so archived reports stay reachable — do not add generation code back. The same goes for `ai-cli` and `ai-ph` (retired October 2026). `REPORT_LABELS` titles stay cadence-neutral because the archive holds both daily and weekly reports.
- **Weekly vs daily.** Trending, the models report, Skills and the Dev.to/Lobste.rs sections run only when `isWeeklyRun` (`src/date.ts`) is true — fetch and report both, except that Trending is fetched daily for agent news. `WEEKLY_REPORT_IDS` (`src/i18n.ts`) is the one list of weekly reports. Measured over September 2026: 54% of trending links and 45% of community links repeated from the previous day. Infra was weekly too (5 of 6 projects shipped no release on a given day) until it became a section of the daily agents report, where a quiet project costs one name. Product Hunt was dropped (mostly consumer apps); ArXiv stays daily pending a quality-ranked replacement.
- **The agents report covers releases, hot issues and news only — no issue/PR churn.** The old per-repo summaries mostly restated ongoing themes ("X remains focused on…"). The pieces:
  - Stable releases only; `isPrerelease` checks the API flag and the tag (`nightly`, `alpha`, `beta`, `rc`, `preview`, `canary`, `.dev`) because several projects publish nightlies as normal releases. Prereleases are counted in the header, never sent to the model — except for a project that has never shipped a stable release (`noStableYet` from `fetchRecentReleases`: the release history fits in one 100-release page and none is stable; a full page of prereleases reads as having a stable one, since Codex runs ~86 alphas per 100). Its newest 3 prereleases in the window (`PREVIEWS_PER_PROJECT`) go to the model under "Prereleases (no stable release yet)" with 1,500 characters of notes stripped of HTML and anchor links (`previewNotes`), and the prompt reports only those with notable features or breaking changes. Added 2026-10-10 for DeepSeek Harness, alpha/rc only, whose 0.2 added a lot of features; at the 400-character stable cutoff its bilingual notes showed only anchor links.
  - `fetchHotIssues` uses the search API (the issues list can only filter by update time). Hot = opened in the window (widened to at least 48h — engagement takes days to build) and `comments + 👍` ≥ 10, or ≥ 3 with a regression/security label; max 2 per repo. Search allows 30 requests/minute, shared with trending's topic queries; `searchSlot` (`src/github.ts`) spaces every search call 2.1 s apart, so each search request costs ~2 s of fetch time, not quota (a trending topic is 1 request daily, up to 4 weekly); a failed hot-issue fetch degrades to none, it never discards the releases.
  - `githubGet` retries a dropped connection twice (2 s, then 4 s), never an HTTP error; search calls retry through `searchSlot`. On 2026-10-06 a connection dropped mid-body (`TypeError: terminated`) and the run lost a Codex stable release, and the report listed Codex with nothing to say.
  - `matchProjectNews` drops an item that names 3+ agents: it is a compatibility list ("works with Claude Code, Codex, OpenCode…"), not news. It also skips an agent's own repo in GitHub Search results — the star-sorted topic queries return QwenPaw every day — but not on GitHub Trending.
  - One LLM call per report over the active projects; quiet projects are listed in one line by `buildProjectReportContent`. A project the model leaves out (its only news mentioned it in passing) is quiet too: `buildProjectReportContent` checks the summary for its `## <name>` heading. The issue body is the full report (no brief variant).
- `callLlm(prompt, maxTokens?)` defaults to 8192 tokens (the highlights JSON and Skills use it). The web report uses `LLM_TOKENS_WEB` = 16384. The agents-report sections, the table-formatted listing reports (discussions, ArXiv, models) and both trending calls use `LLM_TOKENS_LISTING` = 16384. They were 4096/8192/6144 until 2026-10-11, when the free reasoning model's reasoning, which counts against the same budget, cut the HN report off. 16384 is gpt-4o's output cap (the OpenAI and Copilot default model), so a higher budget would break those providers.
- The Skills prompt carries a hard length cap (`REPO_LENGTH_RULE`, ~300 words, max 3 bullets per section). Before such caps the old per-repo reports ran 77–114 KB and hit GitHub's 64 KB issue body limit.
- Data-source listing reports (discussions, ArXiv, models) render their item lists as **Markdown tables** (not bullet lists). Numeric columns are copied verbatim from the fetched data; the summary column is 2 sentences. Trending is the exception: code renders its tables and the LLM fills in only the summaries. Tables already have CSS in `index.html` and render natively in GitHub Issues too.
- Every listing report's body (discussions, ArXiv, models, web, trending) follows one layout: `## Highlights` → the tables → `## Signals` → `## Worth a Look` (the headings are `SECTIONS` in `src/i18n.ts`, each report's own headings — `DISCUSSIONS_REPORT`, `ARXIV_REPORT`, `MODELS_REPORT`, `WEB_REPORT` — sit next to them; web has Highlights, Anthropic, OpenAI, Signals, Worth a Look). The agents report's sections are one `## <Project>` per active project, and Skills has its own four. The prompts give the exact `##` headings and forbid a title (`NO_TITLE_RULE`, `src/prompts.ts`); `stripModelTitle` (`src/report-builders.ts`) still drops a model-written H1 and its `**Date:**`/`**Type:**` block, and `nestHeadings` pushes the Skills body below its `## Claude Code Skills` heading in trending. Before October 2026 each prompt named its own sections ("Today's Highlights" in the weekly HF report, "Community Hot Spots" over a list of repos), and five reports carried two H1s.
- `callLlm` retries on three error classes, with separate budgets; the concurrency slot is released during every wait.
  - **429** — 3 retries, 5 s / 10 s / 20 s. A rate limit clears in seconds.
  - **Connection failure** (DNS/TCP/TLS, detected by `isConnectionError` walking the SDK's `cause` chain) — 6 retries, 5 / 10 / 20 / 40 / 60 / 60 s, capped by `RETRY_MAX_MS`. A network outage between the runner and the provider lasts minutes, not seconds. On 2026-09-03 the DashScope cn-beijing endpoint was unreachable from the GitHub runner for the whole LLM phase; the old shared 3-retry ladder gave up 35 s in and the run published a digest of nothing but "generation failed" placeholders.
  - **Cut-off response** (`TruncatedResponseError`: the provider reports `finish_reason: "length"` or `stop_reason: "max_tokens"`) — 1 immediate retry at double the budget, then the call fails. On OpenRouter the reasoning tokens count against the same `max_tokens` even at low effort. On 2026-10-11 the HN report was published cut off mid-table, missing its last two sections, because the providers returned whatever text had arrived.
- Every LLM call site degrades gracefully (a failed summary becomes a fixed notice), which is right per report and wrong for the run as a whole. `llmStats` in `src/report.ts` counts attempts and final failures across the run, and `assertLlmHealthy(stage)` throws when at least `LLM_MIN_SAMPLES` (3) calls have run and at least `LLM_ABORT_RATIO` (50%) of them failed. `main()` calls it at two gates — after the summary phase and after the save phase — so a provider outage exits non-zero _before_ anything is committed, no issues are opened and no Telegram message is sent (the issues are opened after the second gate, once every report is in). A missing day is recoverable by `workflow_dispatch`; a published day of placeholders is not. `LLM_MIN_SAMPLES` was 5 when a run made ~30 calls; a daily run now makes 3–5 (agents, infra, discussions, ArXiv, web; a section with no activity makes no call), so the first gate only arms on the weekly run and the second gate needs the lower floor to arm at all.
- `reportLlmHealth()` logs the final tally and, when any call was lost, appends a warning to `$GITHUB_STEP_SUMMARY` so a partially degraded run is visible on the Actions run page without a log dive.
- The concurrency limiter (`LLM_CONCURRENCY = 5`) prevents 429s when many parallel LLM calls fire. Do not bypass it by calling SDK clients directly.
- LLM provider is selected via `LLM_PROVIDER` env var (default: `anthropic`). Valid values: `anthropic`, `openai`, `github-copilot`, `openrouter`, `deepseek`, `qwen`.
- The daily GitHub Actions run uses `openrouter` with the free model `nvidia/nemotron-3-ultra-550b-a55b:free` and `OPENROUTER_REASONING_EFFORT=low` (it replaced the stealth model `stealth/space-bunny-alpha`, which expired 2026-10-05). Without the low effort a reasoning model spends the whole `max_tokens` budget on reasoning and returns empty content (`finish_reason: "length"`) — the 2026-10-02 test run lost 19/21 calls that way. Free models can be withdrawn without notice; when that happens the LLM health gate aborts the run, and the fix is a new `OPENROUTER_MODEL` in the workflow.
- The daily workflow only ever produces one digest per CST day. Two mechanisms enforce it: a workflow-level `concurrency: daily-digest` group (`cancel-in-progress: false`) serializes overlapping runs, and a `guard` job skips **scheduled** runs whose `digests/YYYY-MM-DD` folder is already committed (checked via `gh api .../contents/...`, so no second checkout). `workflow_dispatch` always proceeds — that is the escape hatch for regenerating a day. This exists because GitHub delayed the 2026-08-26 scheduled run by 5h07m; the manual catch-up run and the late scheduled run both completed and opened 18 duplicate issues for 2026-08-27.
- Provider implementations live in `src/providers/`. Each file implements the `LlmProvider` interface. The factory in `src/providers/index.ts` validates the provider name and logs only the provider name — never API keys or endpoint URLs.
- `closeSupersededIssues` in `src/github.ts` (run by `pnpm close-stale`, the workflow's last step) keeps only the most recent digest day's issues open and closes the rest — per retention group: all daily labels form one group, each weekly label (`trending`, `hf`; from `WEEKLY_REPORT_IDS`) its own, so Monday's weekly issues stay open until the next Monday. The retained day is the newest **open digest issue**, not today's date, so a failed run leaves yesterday's reports up instead of closing everything. Days are compared as CST dates via `toCstDateStr`, matching the `digests/YYYY-MM-DD` folders — a delayed cron and its manual catch-up run land on the same day and are both retained. Eligibility requires a live report's label (`REPORTS`) (plus the legacy `weekly`/`monthly`, and `digest`/`openclaw`/`ph`/`infra`/`community` from the reports retired or merged in October 2026 — `infra` and `community` count as daily, so their last open issue is closed by the next run), and pull requests are excluded: the `/issues` REST endpoint returns PRs too, and the previous `closeStaleIssues` would have closed any open PR older than its cutoff.
- GitHub issue label colors are defined in `LABEL_COLORS` in `src/github.ts`. Add new labels there.
- Web state (`digests/web-state.json`) is committed to git on every run. It is the source of truth for which URLs have been seen. `buildWebReport` writes it once at the end, regardless of whether a report was generated.
- Tracked repos are pruned when they go quiet. (Since October 2026 a quiet agent costs nothing — it lands in the report's "Quiet today" line — so pruning is less pressing.) Removed August 2026 after an activity audit:
  - `deepseek-harness` — Issues/PRs disabled upstream and the Discussions board dormant: 13/13 days of zero data. Re-added 2026-10-10 at the maintainer's request, now that the report also matches news.
  - `zeptoclaw`, `nullclaw` — no upstream push for 30+ days; 90% and 50% of days had no activity at all.
  - `nanobot`, `nanoclaw`, `lobsterai`, `codewhale` — 17–37 items per 24h, well under the 30-issue + 20-PR prompt sample, so the model was padding a full 8-section report out of a handful of items.
  - `picoclaw`, `moltis` — removed by maintainer decision alongside the above.
  - Same audit fixed two renames: `qwibitai/nanoclaw` → `nanocoai/nanoclaw`, `agentscope-ai/CoPaw` → `agentscope-ai/QwenPaw`.

## Web UI & RSS Feed

- Web UI: `index.html` reads `manifest.json` to build the sidebar, then fetches `digests/YYYY-MM-DD/report.md` on demand. `#YYYY-MM-DD` is the day's overview (each report's `highlights.json` bullets under a link to it; the landing page and the first sidebar entry of each day); `#YYYY-MM-DD/report` is a report, with previous/next-day links, a link to the report's previous day (weekly reports skip days) and, from 4 sections up, a collapsible table of contents (4+ `##`, else 4+ `##` and `###` together: the agents report nests its projects under its two groups). The sidebar pins the latest weekly reports under "This week" (manifest `weekly`); the overview's sidebar label is manifest `overview`. Each report's bar (rendered in code at generation time) links the day's overview and its other reports with absolute Pages URLs, so the same links work in GitHub Issues; in the web UI they navigate via `hashchange`.
- RSS Feed: `feed.xml` at the repo root. Generated by `src/generate-manifest.ts` in the same `pnpm manifest` step. Contains the latest 30 items (newest first) across all report types. Item links use hash routing: `https://dboeter.github.io/daily-diff/#YYYY-MM-DD/report`.
- The daily workflow's "Commit and push digest, manifest and feed" step commits the digest, then `manifest.json` and `feed.xml`, and pushes them once: each push to main starts a Pages build, and two pushes seconds apart made Pages cancel the first build on every run.
- `REPORT_LABELS` in `src/i18n.ts` is the only report label map: the live reports' `REPORTS` names plus the retired ones. `pnpm manifest` publishes it in `manifest.json` (`labels`), which the sidebar (`index.html`) and the MCP server (`mcp/src/index.ts`) read; RSS and Telegram use it too. Until October 2026 a report could carry four names (H1, issue title, sidebar, Telegram) — the infra report was "Agent Tooling Weekly" in its H1 and "AI Infrastructure Digest" in the sidebar.

## Adding a new report type

1. Create a data fetcher (or add to an existing one). For a repo-backed report, add its key to `SECTION_KEYS` in `src/config.ts`: that loads it as a `SectionConfig` (`title`, `subject`, `repos`) and lists it in README.md, which then needs a `<!-- tracked:<key> -->` … `<!-- /tracked:<key> -->` marker pair (`pnpm readme` fills it in). Its prompt wording comes from `PROJECT_SCOPE` (`src/i18n.ts`) and its `subject`. Any other `config.yml` key needs its own `RawConfig`/`RadarConfig`/`loadConfig` entry — a section with no schema entry is silently ignored. Decide daily vs weekly: a weekly report gates its fetch and save on `isWeeklyRun`, and its id goes in `WEEKLY_REPORT_IDS` in `src/i18n.ts`.
2. Add a `buildXxxPrompt` function in `src/prompts-data.ts` (for data-source prompts) or `src/prompts.ts` (for repo-level prompts).
3. Add its emoji, name and issue label to `REPORTS` in `src/i18n.ts` (cadence-neutral: no "daily"/"weekly"); the H1, issue title and labels derive from it.
4. Add a `buildXxxReport` function in `src/data-reports.ts` that returns a `SavedReport`.
5. Wire into `fetchAllData`, `generateSummaries`, and the save phase in `src/index.ts`.
6. Add a label color entry in `LABEL_COLORS` in `src/github.ts`.
7. When retiring a report, move its id into the archive part of `REPORT_FILES` (`src/generate-manifest.ts`) and its label into `REPORT_LABELS`, so its archive stays reachable; live reports are listed from `REPORTS`.
8. Update README.md and this file.
